# dungeonPOE 介面設計流程

任何動到 UI／UX 的工作（再小的調整也一樣）都走這份。上層《塞令老師》的 CLAUDE.md 寫的「apple-design 為主」在這裡不適用。

**先當最挑剔的玩家，再當工程師。**「面板沒出畫面、按鈕夠大、測試通過」只是地板，不是做好了。2026-11-13 使用者：「你自己查看都不會覺得有些地方設計很爛嗎」。0.4.4～0.4.6 每一版測試都過，手機上還是又卡又怪（按一下要 100～600 毫秒才有反應、天賦樹每個點 6px、可以按的東西有六種長相）。所以：

- **改之前**：在手機尺寸實際操作一次要改的流程，截圖，**寫下爛在哪**（不是「有沒有跑版」，是「我是玩家會不會煩」）。
- **改之後**：再操作一次。回覆裡除了改了什麼，**一定要有「還是爛的地方」**；一條都寫不出來，代表沒有認真看。
- 使用者說「怪」「卡」「不好用」時，不要先辯護現況，先去量、去操作。

**重做一個畫面之前，先查它是不是使用者定稿的設計。** Grep `CHANGELOG.md` 與 `docs/企劃書.md` 找那個畫面（「原型」「定稿」「照原型」）。是的話骨架不能換，只能在裡面修具體的問題，而且先問要修哪些。2026-11-13：技能面板的齒輪圓環是 0.2.75 定稿的原型，我把直立改成一招一列的清單，使用者：「怎麼又改回舊版 uiux」「改的比之前還爛」，整個退回。昇華石碑能重做，是因為那張圓盤只是照天賦樹順手畫的，沒有定稿過。

## 誰說了算

| 管什麼 | 照誰 |
| --- | --- |
| 長相：顏色、字體、框、層級、版面、文案 | `DESIGN.md`。`docs/介面規範.md` 的數值跟 `DESIGN.md` 不一致時，改規範 |
| 互動手感：回饋、可打斷、跟手、進出、減少動態 | 下面的 apple-design 清單 |
| 技術限制、測試尺寸、元件 | `docs/介面規範.md`（別的 skill 不能推翻）；操作規則在 `docs/企劃書.md` 第 9 節 |

## 每個畫面先回答（動手前寫在回覆裡）

1. **玩家來這裡想做什麼**：一句話，從玩家的角度寫（「看有沒有比身上好的鞋子」），不是系統的角度（「顯示倉庫清單」）。
2. **從哪裡來、做完去哪裡**：幾下點得到？做完要回去的地方一下回得去嗎？
3. **最常做的那一件事幾下完成**：數出來。多於三下就要有理由。
4. **每一種狀態長怎樣**：空的、滿的、不能用（寫原因）、正在等。只畫「有東西」的那一種不算做完。
5. **進出有沒有過場**：瞬間出現、瞬間消失會讓人覺得卡。

## 檢查表（改之前、改之後各對一次）

### 順（用量的，不要用感覺）

`node tools/ui_perf.js`（要先開本機伺服器；手機直立、CPU 降速 4 倍）：

- **按下到畫面更新 ≤100 毫秒**；超過 200 玩家會覺得卡。量的是瀏覽器的 Event Timing，包含等遊戲那一格畫完的時間，不是只有我們的函式跑多久。
- **捲清單、拖曳、縮放每一格 p95 ≤33 毫秒**。
- **打開一個畫面 ≤200 毫秒**。
- 戰鬥在跑時，開著的面板不要因為撿到東西就整片重畫；整片 `innerHTML` 重畫會打斷正在捲的清單。
- 改之前先跑一次記下數字，改之後再跑一次，兩組數字都附在回覆裡。**數字變差就是改壞了**，即使看起來比較漂亮。

### 按得到、按得準

- 點擊區至少 44px（圖示可以小，點擊區要夠大）；主要動作在拇指搆得到的下半部。
- **只有圖示的按鈕不准用在會消耗東西的動作上**（手機沒有滑過的說明，要知道是什麼只能點）。
- 手指在清單的格子上滑＝捲清單，不能把東西拖起來。
- 會被手指擋住的東西（說明框、選單）不要蓋住被點的那個東西。
- 一開始看到的大小就要認得出內容：天賦點、地圖節點至少 24px，不能要玩家先放大才看得到。

### 看得懂

- 每個畫面只有一個放大的數字、一個主要按鈕。
- 不能用的東西要變暗**並寫原因**；選到的東西要亮起來並捲進畫面。
- 不只靠顏色：有顏色意義的地方另外要有圖示、形狀或字。
- 帶遊戲資訊的字對比至少 4.5:1；壓在戰鬥畫面上的字要有描邊或底，不能直接疊在特效與跳數字上。
- HUD 不擋畫面中央；同時出現的 HUD 元件有上限，新加一個先問能不能拿掉一個。
- 字不小於 `docs/介面規範.md` 的下限（面板 11px、HUD 10px）。

### 一致（「整體很怪」多半是這個）

- **同一件事在每個畫面長一樣、放同一個位置**：關閉在右上、主要動作在底部、返回的方式一樣。
- 新的長相動手前先問「`docs/介面規範.md` 第 3 節哪個元件可以用」；真的沒有才新增，並寫回規範。**可以按的東西不要每個面板各做一套**。
- 字體：襯線只給標題與主要動作，其他一律黑體；同一排按鈕不混兩種字體。
- 圖示只用一種語言：道具與技能是像素圖，介面的小圖示是 `ICO` 的線條圖；不要同一排有的有圖示、有的沒有。
- 面板開關、分頁切換的過場用同一組時間與曲線（規範第 4 節）。

## 依改動大小做到哪

1. **小調整**（改字、移一個按鈕、調間距）：改之前、改之後各截一張圖對照。
2. **改一個面板**：再加手機四個尺寸的 `tools/touch_check.js`、桌機兩個尺寸的截圖、`tools/ui_perf.js` 前後的數字。
3. **新畫面或改版**：先回答上面五題、在手機上把現在的流程實際走一遍並列出問題，給使用者看過再動手；做完更新 `DESIGN.md` 與 `docs/介面規範.md`。
4. **動到互動、動畫、拖曳、手勢**（不分大小）：另外啟動 `apple-design`，有動畫再加 `animate`；手機才有的問題參考 `mobile-native`。

## apple-design 清單（實際操作，不要只看程式碼）

- 按下就有回饋（`:active` 縮小），放開才執行；拖曳跟手，抓哪裡就跟哪裡，放開從現在的位置過去。
- 動畫可以被打斷、不擋操作；從畫面上現在的值開始動，不跳。
- 面板、說明框從造成它的東西長出來，進出走同一條路。
- 系統「減少動態」時只淡入淡出。
- 點擊區至少 44px；手機主要按鈕在拇指搆得到的地方。

## 步驟

1. **找程式**：Grep `docs/CODEMAP.md`；面板開關是 `js/hud.js` 的 `openPanel('…')`／`hudPanels()`，HUD 文字用 `setT` 更新，canvas 上的框用 `render.js` 的 `frameRect`。
2. **改之前截圖**：在 `dpoe/` 底下開 `python3 -m http.server`（上一層 `.claude/launch.json` 的 `dungeonpoe` 也行，port 8003），網址加 `?p=2` 用測試存檔。最擠的情況也要試（背包滿、詞綴最多、名字最長）。
3. **改**：只用 `css/style.css` `:root` 的變數與 `docs/介面規範.md` 第 3 節的共用元件；JS 不寫死顏色、字級。
4. **檢查與改之後截圖**，跟改之前並排給使用者看：
   - 桌機 1440×900、1280×720：面板不能超出畫面。
   - 手機橫向 844×390、667×375，直立 390×844、375×667：`node tools/touch_check.js 寬 高 [網址]`（要先開本機伺服器）。
   - 字不小於 10px、按鈕不重疊、主要按鈕看得到。
   - `node tools/ui_perf.js`：跟改之前的數字比。
   - 本機改了 CSS／JS 瀏覽器可能用快取：對每個 script／stylesheet `fetch(url, { cache: 'reload' })` 後 `location.reload()`。
5. 照 CLAUDE.md：prettier、codemap、CHANGELOG；新的元件寫進規範第 3 節，新的互動規則寫進第 4 節。
