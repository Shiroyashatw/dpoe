# 野心：把任務想大、想深、想廣

限制成果的通常不是模型能力，是任務被想得太小：拆成小步驟、照外行的做法、困在成品名稱裡。問一個做不到的問題，代價只是幾分鐘，所以先想大的，不行再縮。動手前照下面三軸各問一次，把「更大的版本」提給使用者挑。

## 什麼時候跳過
- 小修正、錯字、使用者已經講清楚怎麼做的指令：直接做，不提更大的版本。
- 同一件事只提一次；使用者選了小的就照小的做，不再推。

## 1. 高度：要結果，不要步驟
- 一直問「做完這件事，然後呢？」，一層層往上推，直到使用者真正要的結果。例：「修這個 bug」→「讓遊戲不當機」→ 自己找出當機原因、修、測。
- 推到做不好就退一層（需要只有使用者才有的資訊、超出一次對話的規模、要碰正式資料），那一層就是能交的最大目標。
- 在 dungeonPOE：最上層通常是「玩起來好玩」（`docs/設計原則.md`，MDA 從樂趣倒推），所以數值、機制的任務往上一層多半是「這改動讓哪種樂趣變好、怎麼證明」。

## 2. 深度：專家的方法，不是專家的口氣
角色扮演（「你是資深企劃」）只換語氣，不算。動手前先回答四題（要查資料就派子 agent）：
1. 這個領域最頂尖的人會做哪些一般人沒想到的事？
2. 他們看哪些第一手資料，而不是別人整理好的？在專案裡：實際跑遊戲、`tools/dmg_check.js` 等工具的數字、真實存檔，不是猜。
3. 他們用哪些具體的方法和工具？
4. 做完怎麼證明真的有用，而不是「看起來不錯」？先寫好驗證方式再動手。

## 3. 廣度：名詞換動詞，跨行業借做法
- 成品名稱（「天賦樹」「商店介面」）會把思考鎖在那個行業裡。先換成它要發揮的作用（「讓玩家每升一級都有想點的東西」），再問：哪些不同行業的人最擅長做到這件事？他們的手法怎麼套過來？
- 例：「做首頁」→「五秒內讓陌生人停下來並好奇」→ 借預告片剪輯、短影音、櫥窗設計的手法。

## 不合理目標（選用）
目標只會帶出小修小補時，換成極端數字（10 秒 → 0.2 秒），逼出完全不同的做法。保險：
- 一定附量測方式，用數字說話。
- 碰到真正的物理或規則極限就照實說：極限在哪、離極限多遠。絕不宣稱達成做不到的事。

## 怎麼提出來
- 跟 `grilling` 一起用時，更大的版本放進當輪的問題；推薦答案寫真心認為最好的那個，可以是小的。
- 格式：原本的任務 → 拉高／拉深／拉廣後的版本（一兩句）→ 多花多少工、多得到什麼 → 怎麼驗證。
- 使用者點頭才做，不自己偷偷擴大範圍。實作時照 `ponytail`：這裡決定做什麼，`ponytail` 決定怎麼用最少的程式做完。

## 給使用者的提問句型（使用者問「怎麼問 AI」時給）
- 結果式：「我真正要的結果是 ___，你負責把它做到，怎麼拆你決定。」
- 然後呢：每輪結果出來後問「然後呢？」；最上層問「這件事真正的目的是什麼？有沒有比 ___ 更好的做法？用過去的資料證明它比較好。」
- 專家四問：上面深度那四題，叫 AI 動手前先答。
- 動詞化：「我想要 [動詞＋效果]。哪些不同行業的人最擅長做到？手法是什麼？怎麼套到我的情況？」
- 不合理目標：「我要做到 [極端數字]。」被說不可能時：「先列出做不到的真正原因和極限，再想完全不同的做法。」
