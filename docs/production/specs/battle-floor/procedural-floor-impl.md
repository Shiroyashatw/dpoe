## 1. 算法

逐步照 `make_tile`（`base_r2.py:33-61`）。輸入一顆 32×32 亮度樣板、一個 RNG、以及 `light`／`decor`。輸出 64×64（32 先算完，再 `Image.NEAREST` 放大 2 倍，:61）。實機世界格是 48 px、桌機 `ZOOM=1.35`（`js/game.js:477` 的 `TS=48`；桌機 `ZOOM=1.35` 見 `js/render.js:120,126`、`js/main.js:187`），一格畫面約 64.8 CSS px，與示意 64 px 差 0.8，對圖允許 ±1 CSS px（起點，待實測）。`imageSmoothingEnabled=false`（`render.js:127`、`biome.js` `bakeChunk`）維持。

### 1.1 亮度樣板

用 **`art/tiles/lava/floor/tile_lava_floor-s1202.png`**（32×32，283 B，md5 `026e5d66…`），不要用 `tile_d2_battle_floor-s5201.png`。

`TILESRC['D2']` 就是這張岩漿磚（`base_r2.py:32`）。`tlum`（:30-31）：讀成亮度 L，再 `(L − median) / (std + 1e-6)`。磚縫遮罩：標準化值 `d < -1.1`（:43）。s1202 縫佔 12.207%（125 px）；s5201 只有 9.277%（95 px），而且縫是長直角，鋪出來不像營地示意圖。對照見 `evidence/battle-floor/gen-384x256-s1202.png` 與 `gen-384x256-s5201.png`（同一 seed、同一套算法）。s5201 只當「目前實機暫代平鋪」的原檔，不拿來當本算法樣板。

### 1.2 對到 token

`p['ground']`／`p['mid']`／`p['light']` 用 M2-36 `--scene-X-ground`／`--scene-X-mid`／`--scene-X-light`：

| token | 值 | L*／C*／h（本機 CIE Lab D65 實算，對得上 M2-36 第 22–24 行） |
|---|---|---|
| `--scene-X-ground` | `#46413c` | 27.87／3.97／73.8 |
| `--scene-X-mid` | `#33302b` | 20.01／3.69／86.0 |
| `--scene-X-light` | `#615b56` | 39.06／4.01／69.1 |

Lab←sRGB 用 CIE Lab D65（與 `d2final/lib.py:8` 的 `colour.XYZ_to_Lab` 相同）。Lab→sRGB 用 `base_r2.py:23-29` 的 `lab2rgb_np`（D65、sRGB 逆 gamma；`t³>0.008856` 分界）。

底色 L*（:38-39）：淺磚 `base = lL`，否則 `base = gL`。`alt=True` 時才用 `(gL+mL)/2`，營地示意圖呼叫沒傳 `alt`（`render_final.py:16`），實機不要開。a*b*：淺磚用 light 的，否則用 mid 的（不是 ground 的 a*b*）。

### 1.3 雜訊、縫、污點（數字全部來自 :40-59）

1. 整磚 L* 偏移 `off ~ Normal(0, 1.6)`（:40）。
2. 先在 16×16 抽 `Normal(0, 1)`，用 `kron` 放大 2 倍後乘 1.4，再加一層 32×32 的 `Normal(0, 0.7)`（:41）。`L = base + off + n`（:42）。
3. 縫（`d < -1.1`）改寫成 `mL + Normal(0, 0.6)`（:43-44）。
4. 縫的亮邊：縫的下／右鄰且本身不是縫，`L += 2.6`（:45-46）。
5. 縫的暗邊：縫的上鄰，且不是縫、也不是亮邊，`L -= 1.8`（:47-48）。（沒有左鄰暗邊。）
6. a*、b*：底值加 `Normal(0, 0.35)`；縫改回 mid 的 a*／b*、不再加這層雜訊（:49-50）。
7. 污點：`decor = int(rng.integers(0, 4))`（`render_final.py:16`），即 0–3 次。D2 不是 D3，走 else（:57-59）：在 `[2, 30)` 抽一點，`L -= 4`；50% 再把右鄰（若 x+1<32）`L -= 3`。不改色相（沒有 D3 那種 `A -= 1`）。

沒有再疊整場漸層、暗角或 CSS filter。燈籠光暈是另層（見 §5），不要烤進地磚。

### 1.4 翻轉／轉置

樣板在上色前（:35-37），各 50% 獨立：左右翻、上下翻、轉置（等於 90°）。三次都做得到 8 種朝向。實機在生成變體時做完，畫的時候不要再翻。

### 1.5 淺磚次數（無盡戰場）

示意圖（`render_final.py:120-127`）：戰場框內，格心落在寬／高 20%–80%（面積 36%）時 4%，否則 12%；另強制主角右側那一格為淺磚。期望次數 `0.36×0.04 + 0.64×0.12 = 9.12%`（不含強制格）。

實機是無盡捲動，視窗相對的「中央／外圍」不能寫進 `bakeChunk`（鏡頭一動，同一世界格的「中央」會變，重烘就不穩）。不要做視窗相對次數。

**改為世界座標每格獨立抽籤，單一次數。** 起點（待實測）：**9.4%**。來源：對營地底圖在 y=36+64k、x=64k 網格（桌機 top=36，`render_final.py:116-118`）量 20×9 格，用已知普通磚／淺磚平均 L* 的中點門檻 32.05（本機校準：普通 μ=27.20、淺磚 μ=36.89，100 張抽樣假陽／假陰皆 0）得到全場淺磚 9.44%，與算法期望 9.12% 接近。M2-36 第 24 行：畫面中央 60% 內淺磚 ≤ 10%；單一次數 9.4% 時期望也是 9.4%。底圖中央實測 13.3% 很可能含主角／特效／預警，不當目標。示意圖裡「強制淺磚在我方特效下」是構圖需要，無盡戰場不做。

抽法：`h(tx, ty, 1) / 2^32 < 0.094`（或等價 `h(tx,ty,1) % 1000 < 94`）。`h` 用現有 `js/core.js:6-10`。

### 1.6 種子

示意圖整張共用一個 `numpy.random.default_rng(seed)`（`render_final.py:111`，範例 seed=7），格與格的亂數是一條流。實機區塊會重烘，必須改成**每格獨立、由世界格座標決定**，重烘才不變。這是必要差異。

用現成 `h(x,y,s)`（`core.js:6-10`）與 `rng(seed)`（:12-19）：

- 是否淺磚：`h(tx, ty, 1)`（§1.5）。
- 生成該格（朝向、雜訊、污點）：`rng(h(tx, ty, 0))`。若採載入時變體庫，則 `h(tx, ty, 0) % N` 抽庫內第幾張（變體本身在載入時已用固定種子生成）。

`tx, ty` 是地圖格座標（與 `bakeChunk` 裡 `h(cx * BCH + x, cy * BCH + y)` 同一套，`biome.js:372`）。

numpy 的 PCG64 與 JS `rng()` 不是同一個產生器。採變體庫則兩邊只要「同一格永遠抽到同一張」即可，不必重現 numpy。若當場生成、要跟本檔示意預覽逐像素相同，才需要把 `lab2rgb_np`＋本節種子在 JS 對齊；不要求逐像素等同 numpy（起點，待實測）。

## 2. 實機接法

現況：main `53e1bbad` 的 temple 地板仍是 `tile_temple_floor-s1103`。PR #211（`feat/battle-floor-shared-1126` @ `29615bea`，不合併）改接單張 s5201、全地點 `BIO_ONE='temple'`，`T.floor.length===1`，不翻轉。`bakeChunk` 仍是 `CX.drawImage(T.floor[h(...) % T.floor.length], x*32, y*32)`（main 與 #211 都沒改這行）。測試已留「以後 `picked.txt` 多一行就是多一種」。

**建議：載入時生成變體進離屏 canvas，接上既有 `T.floor`／`bakeChunk`。** 不要每幀生成。

- **N（起點，待實測）：普通 32 ＋ 淺磚 16，共 48 張** 32×32。記憶體 48×32×32×4 = 196,608 B（未計 canvas 額外開銷），可忽略。本機 Python 生成約 1.2 ms／張，48 張約 58 ms，只在載入付一次。可見範圍約 20×11 格，雜湊打散後會重複，但不應成網格（待實機目視）。
- **另一條：每世界格當場生成並快取。** 最接近示意圖「每格獨立雜訊」。一區塊 8×8=64 張，本機 Python 約 77 ms；JS 可能更慢，第一次走進新區塊可能頓（待實測）。若量到明顯卡頓，退回變體庫。

`TILE_SRC`／`picked.txt`：本算法是載入時用 s1202 當樣板**生成**，不是再挑一張 PixelLab 平鋪圖。s1202 仍留在 `art/tiles/lava/floor/` 給生成器用；不要把它寫進 `TILE_SRC.temple.floor` 當唯一平鋪。生成結果掛上 `TILES.temple.floor`（或分成 `floor`／`floorLight` 兩組再按 §1.5 選）。

分地形上色：目前 `BIO_ONE='temple'`，全地點共用。若日後分地形，只換 `--scene-<地形>-ground/mid/light`（main 的 `--scene-temple-*` 仍是舊值 `#1c181e`／`#6a241b`／`#a63c2b`，`css/style.css:253-255`，**不是**本地板要用的 X 套值）。本輪不分工地形色票；未另給套值前，全部地點用 `--scene-X-*` `#46413c`／`#33302b`／`#615b56`。

## 3. 驗收

### 3.1 參照裁切

`docs/production/evidence/battle-floor/ref/floor-384x256.png`：從 `bg_battle_1280_noidle.png` 裁 `(0, 356, 384, 612)`（384×256，對齊 y=36 的 64 px 格網）。右側仍切到掉落牌「判」一角，對圖時避開右 64 px。此裁切沒有過門檻的淺磚（24 格中 0 格；格平均 L* 22.02–29.47，全距 7.45）。像素三分（Lab 最近的 ground／mid／light）：81.1%／16.5%／2.4%。

淺磚次數與全距請對大範圍：同底圖 `(0, 100, 1280, 676)` 共 180 格，淺磚 9.44%，格 L* 20.98–40.89（全距 19.91）。另存 `ref/floor-384x256-has-units.png`（`(0, 292, 384, 548)`）可見一塊淺磚，但上緣有單位，只供看明暗，不作疊圖主參照。

空場預覽（已標「示意」）：`preview-1280x720-示意.png`，單一次數 9.4%、世界格種子。本機實抽約 7.5–7.7%（220 滿格），格 L* 23.77–39.54，全距 15.78。純地板 C*>40 面積 0%，C* 最大 5.93（≤ 場景紋理 6）。

### 3.2 實機對圖

工程師雲端場次拍 **桌機 1280×720、無敵人、無掉落、無預警／技能** 的戰鬥地板（進圖後清怪或開空場測試）。裁與參照同格網、同 384×256（或 1280 寬、高 256 的條）。390 本項只跑 touch_check，不以 390 地板當通過條件。

通過（空場）：

- 淺磚佔比與 9.4% 相差不超過 3 個百分點；畫面中央 60% 內 ≤ 10%。
- 鄰格平均 L* 全距 ≥ 7（參照小裁切 7.45；大範圍可到約 16–20）。單張 s5201 平鋪做不到這種全距。
- 磚縫長相接近 s1202 樣板（短、錯落），不要變回 s5201 的長直角縫。
- 純地板（不含單位／光暈／預警）C*>40 面積 ≈ 0，場景中位 C* ≤ 6。
- 目視無整排重複網格。縮放差 ±1 CSS px 可接受。

疊圖用參照裁切時，忽略右緣掉落牌殘留。
