# 匿名漏斗與留存量測（Q18 B：最小匿名漏斗）

> 現行規格，只放目前有效的內容；決定與調整記在 [`CHANGELOG.md`](../CHANGELOG.md)。實作是 M2-27。標「假設」的是製作人提案，待 mumi 驗收；驗收前 M2-27 照本文做。

## 1. 範圍與原則

- 只為了量 [M2-03](M2-03-addictiveness-criteria.md) 的真人指標 R1、R3–R6，與 R2 的「第幾分鐘關掉」。A1–A10 照舊由 AI 試玩量，不靠漏斗。
- **不收任何個資**：不收信箱、帳號 ID（Supabase `user_id`）、IP 欄位、User-Agent、螢幕尺寸、語言、時區、來源網址、存檔內容、裝備與數值。
- **不做帳號連結**：漏斗編號跟 Supabase 帳號、`dungeon_saves`、存檔都不相連；登入、登出、註冊都不換也不上傳漏斗編號。現有的訪客／信箱帳號照舊，不新增任何連結。
- **只用匿名 ID**：每台裝置（瀏覽器）第一次開遊戲時隨機產生一個編號，只存在本機。
- 最小集合：4 種事件、每個事件 ≤ 6 個欄位；新增事件或欄位要先改本規格並記 CHANGELOG。

## 2. 匿名編號與本機紀錄

本機 `localStorage` 一個鍵 `dungeonpoe-funnel`（跟存檔 `KEY+SLOT`、Supabase 登入資訊分開；**不放進 `S`**，所以不會跟著雲端存檔上傳），內容：

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `fid` | 字串 | `crypto.randomUUID()`；沒有就 16 個隨機 hex。只用來把同一台裝置的事件串起來 |
| `d0` | 整數 | 第一次開遊戲那天的本機日序（`Math.floor((Date.now() - 時區偏移) / 86400000)`），只存在本機，不送出 |
| `off` | 0／1 | 玩家在設定關掉匿名統計＝1 |
| `sent` | 物件 | 「只送一次」的事件記號（`craft`、各 `node` 索引），避免重送 |

- 清除網站資料、換瀏覽器或換裝置＝新編號、新的 `d0`（D1／D7 會少算，寫在報告限制裡）。
- 多個存檔欄位（`?p=`）共用同一個編號（假設：同一個人）。

## 3. 事件清單

共同欄位（每個事件都有，全部由前端填，不填其他東西）：

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `fid` | 字串 | 第 2 節的匿名編號 |
| `sid` | 字串 | 這次開遊戲隨機產生的 8 個 hex，不存檔；用來算單次時長 |
| `ev` | 字串 | 事件名，只能是下表四種 |
| `v` | 字串 | 遊戲版本 `VER` |
| `day` | 整數 0–400 | 距第一次開遊戲第幾天（今天日序 − `d0`）；超過 400 寫 400 |
| `pf` | 字串 | `port`（手機直立）／`land`（手機橫向）／`pc`（桌機），照 `TOUCH.on` 與 `PORT()` |

伺服器端只加 `at`（收到的時間，資料庫預設 `now()`）。

| 事件 `ev` | 什麼時候送 | 額外欄位 | 量哪個指標 |
| --- | --- | --- | --- |
| `open` | 每次開遊戲、`S` 準備好之後（開場也算）送一次 | `fresh`：0／1，這次是新存檔（走開場或 `proGive` 的 `fresh`）＝1 | R5、R6；`fresh=1` 定義世代 |
| `alive` | 這次開遊戲累計前景時間（`document.hidden` 時不算）到 1、3、5、10、20、30、45、60、90、120 分鐘各送一次；120 分鐘之後不再送 | `m`：上面那十個數字之一 | R1（單次時長）、R2（第幾分鐘關掉） |
| `craft` | 這台裝置第一次 `craftDo` 成功（扣了材料、做出至少一件）；只送一次 | `sec`：從這台裝置第一次 `open` 到現在的累計前景秒數，上限 7200 | R3 |
| `node` | 第一次開刷主幹第 `i` 個地點（`runNode` 成功、`TRUNK_K.indexOf(k) = i`）；每個 `i` 只送一次；特殊節點、裂口不送 | `i`：主幹索引 0 起；`sec`：同 `craft` | R4（`i ≥ 1`）；前期推進漏斗 |

- `craft`、`node` 的 `sec` 要靠本機多記一個累計前景秒數 `fs`（只存在 `dungeonpoe-funnel`，到 7200 停止累加）；它是 M2-27 的實作欄位，不送出 `fs` 本身。
- 舊存檔的裝置第一次升到含漏斗的版本時：建立編號、送 `open`（`fresh=0`）；`craft` 若存檔裡已打造過就把記號標成已送、不補送（假設：M2-27 用存檔現有的任一打造痕跡判斷，找不到就照常送，報告只算 `fresh=1` 世代所以不影響指標）。
- 一次開遊戲最多送 1＋10＋1＋主幹地點數 個事件，前期通常 ≤ 15 個。

## 4. 指標怎麼算（只算 `fresh=1` 世代：第一個 `open` 是 `fresh=1` 的 `fid`）

| 指標 | 算法 |
| --- | --- |
| R1 第一次遊玩時長（中位數） | 世代裡 `day=0` 的第一個 `sid`，取它最大的 `alive.m`（沒有＝<1）；中位數 ≥ 30＝達標。精度到上面的分鐘檔 |
| R2 第幾分鐘關掉 | 同上，列出最大 `alive.m` ≤ 10 的人各停在哪一檔，配合當時最後一個 `node`／有沒有 `craft`。「因為不知道要做什麼」仍要觀察記錄判斷 |
| R3 5 分鐘內第一次打造 | 世代裡 `craft.sec ≤ 300` 的 `fid` ÷ 世代人數 |
| R4 玩到第 2 個地點 | 世代裡有 `node.i ≥ 1` 的 `fid` ÷ 世代人數 |
| R5 D1 | 世代裡有 `open.day = 1` 的 `fid` ÷ 第一個 `open` 已滿 2 天的世代人數 |
| R6 D7 | 世代裡有 `open.day = 7` 的 `fid` ÷ 已滿 8 天的世代人數（假設：用固定第 7 天；報告另附「第 7–13 天任一天」供參考） |

- 每版分開算（`v` 取世代第一個 `open` 的版本）；樣本 < 20 人只列人數不列比例（M2-03：Q19 C 第二階段 20 位以上）。
- `pf` 分開列，看直立／橫向／桌機差異；不另做裝置細分。
- 算法寫成 SQL（M2-27 附在 `tools/` 或規格附錄由實作者決定），製作人在 Supabase 後台執行；不做前端報表。

## 5. 傳送與儲存

- **表**：Supabase 同一專案，新表 `public.dungeon_events`（跟 `dungeon_saves` 分開）。欄位就是第 3 節：`fid text, sid text, ev text, v text, day smallint, pf text, fresh smallint, m smallint, sec smallint, i smallint, at timestamptz default now()`；**沒有 `user_id`、IP 或任何其他欄位**，不設 `default auth.uid()`。
- **RLS**：`anon` 只能 `insert`、不能 `select`／`update`／`delete`；check 限制 `ev` 只能四種、各欄位長度與範圍照第 3 節。讀資料只在 Supabase 後台由製作人做。前端只用 anon key，**絕對不用 service_role key**。
- **送法**：直接 `fetch` 到 `SB_URL/rest/v1/dungeon_events`，標頭 `apikey` 與 `Authorization: Bearer` 都放 anon key（**不帶玩家登入的 JWT**，所以請求裡沒有帳號 ID）、`keepalive: true`、`Prefer: return=minimal`。送失敗就丟掉，不重試、不排隊（少算可接受）。
- **不送的情況**：`off=1`；本機與測試入口（跟 `cloudInit` 同一條：`TEST` 或 localhost 且沒有 `?cloud=1`）；`window.fetch` 不存在。測試用一個可替換的送出函式攔下事件檢查格式，不碰正式庫。
- **保存期限**：原始事件 **90 天**（假設：夠看 D7 與連續幾版比較）；每天由 Supabase 排程（`pg_cron`）刪 `at < now() - interval '90 days'`。若專案方案不支援排程，製作人每月手動刪一次並記 CHANGELOG。需要長期留的只留每版彙總數字（人數、比例），寫進 M2-10／M3 的報告，不留原始事件。
- 平台日誌：Supabase 的 API 閘道日誌會依方案短期保留請求資訊（含來源 IP），這不是本表、我們不匯出也不分析；隱私說明照實寫「伺服器紀錄依服務商短期保存」（假設：待製作人查方案保存天數後補數字）。

## 8. M2-27 交辦條件

M2-27 照本規格實作，完成標準：

1. 第 2 節本機紀錄、第 3 節四種事件、第 5 節送法與「不送的情況」；不改其他遊戲邏輯與數值，送出失敗不影響遊戲。
2. Supabase：建表、RLS、`pg_cron` 刪 90 天（SQL 寫在 `docs/本機執行.md` 或規格附錄，由製作人／mumi 在後台執行；前端不放 service_role key）。
3. 第 6 節設定面板一節與「更多」副標，照第 7 節順序；兩尺寸截圖。
4. `check.js` 新增：事件只有四種、欄位只在白名單（第 3 節）、沒有 `user_id`／`email`／`uid`／UA 類字串、`off=1` 與本機不送、`alive` 只在十個分鐘檔送一次、`craft` 與同一個 `node.i` 只送一次。

7. 改 `VER`（照 CLAUDE.md 版本規則），PR 附 A1–A10 指標表。
